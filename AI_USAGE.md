## Tools and models

- **Claude Code** (VS Code extension), one session. Models: Claude Fable 5.2
  for planning, the first build and the later redesign; Claude Opus 5.5 for
  the first review round. It read the brief, proposed the design, wrote the
  code, tests and first drafts of these documents, and ran the checks.
- **Review subagents**: four independent Claude Code reviewers, started in
  parallel from the same session, each given only the brief and the code (not
  the builder's conclusions). See moment 6.
- **A second AI assistant** produced one screen-by-screen UI audit, which I

## Agent instruction files (committed)

- [`AGENTS.md`](AGENTS.md): the project's rules for any AI agent. Eight
  boundaries that protect the seams, how to work, and the checks to run.
  Rule 8 (no page may assume how much data arrives) was added after the
  redesign, from a mistake the AI made (see "wrong", item 8).
- [`CLAUDE.md`](CLAUDE.md): points Claude Code at `AGENTS.md`.
- [`web/AGENTS.md`](web/AGENTS.md): generated by Next.js. It tells agents that
  this Next.js version differs from their training data and to read the docs
  bundled in `node_modules/next/dist/docs/` first. This file mattered twice:
  see "where the AI got something wrong", items 2 and 3.

## Plan

There was no separate spec file. The plan was agreed in the chat before any
code, in this order:

1. The AI read the brief and listed the acceptance criteria, the hard rules
   and the gaps left on purpose.
2. Stack chosen, then the two risky parts of that choice settled (below).
3. Each technical constraint mapped to a concrete approach, one row each
   (stack, data only through the backend, AWS-compatible containers, one
   command to run, no secrets, no paid services).
4. Build order: backend rules and tests first, then the HTTP layer, then the
   client, then containers, then a full run in a real browser, then documents.
5. Independent review by four reviewers, fixes, and a full re-verification.
6. A redesign of the client, page by page, then a second independent review.

## Key prompts and moments

1. **"Understand the prompt and tell me."** I asked for the brief to be
   explained before asking for any code. The useful output was the list of
   gaps the brief leaves open (who chooses the five products, where the email
   goes with no paid provider), which became the assumptions table in
   `DECISIONS.md`.

2. **"MERN Next Typescript."** My stack choice. The AI did not just accept it.
   It raised two problems:
   - Next.js can act as a backend too, which would blur the frontend/backend
     boundary the brief scores. Rule adopted: Next.js renders pages only, and
     Express owns all data and rules.
   - MongoDB is not needed for the catalogue, because Fake Store already
     returns products, categories and ratings. It offered three options (small
     role, cut it, copy all products in) with the trade-off of each, and
     recommended the small role: featured ids and enquiries only.

3. **"I want to be the best guy to solve this problem."** I did not pick
   between the three MongoDB options; the AI went ahead with its own
   recommendation. That was its decision, not mine.
   TODO(Arun): say here whether, after reviewing it, you kept that decision
   and why (or what you changed).

4. **"Check the technical constraints and tell me what should be the proper
   way."** I stopped the build to have each constraint checked against the
   plan. This surfaced the one real risk in my stack choice: a reviewer asking
   "which one is your backend?". The answer is now stated in the README.

5. **"Run it locally so I can see it."** Docker could not run on the build
   machine (no Windows Subsystem for Linux, no admin rights to install it).
   Instead of claiming the app worked, the AI ran a real MongoDB binary and
   Mailpit, started the built backend and the client in its Docker form (the
   standalone server), and I used it in the browser.

6. **"Run council review and make sure we have the best product and it is
   possible to run in 10 minutes for review."** Four reviewers ran in parallel:
   one acting as the hiring reviewer trying to run it in 10 minutes, one as a
   panel principal engineer scoring the five areas, one on backend
   correctness and security, one on the client in a real browser. Each was
   told to mark findings "verified" or "suspected" with file and line. Several
   findings were raised independently by two or three reviewers, which is how
   I judged they were real. Every high and medium finding was fixed or, where
   fixing was the wrong call, written down honestly in `DECISIONS.md`.

7. **"UI looks good?" then "I don't like the design."** The AI's own review
   said the first look (warm off-white, serif headings, green accent) was
   "good enough" and recommended four small CSS fixes. I disagreed and
   rejected the look. It then offered three directions; I picked two (white
   and minimal, black and sharp), and it built them as the light and dark
   modes of one design, one page at a time, showing me each before the next.
   The taste call was mine; the AI's first instinct was to defend its work.

8. **"Zoom 100 should fit the screen" and "even if we add more data to the
   API it should work seamlessly."** Two requirements I added that the brief
   does not state. The AI turned them into something checkable: a script
   that opens every page at four window sizes in light and dark and compares
   page height with window height. To test "more data" for real, it pointed
   the backend at a 194-product, 24-category sample served in Fake Store's
   shape (one setting, `FAKESTORE_BASE_URL`; no code change). That run is
   what found three layout bugs (see "wrong", item 8). The sample data is
   not in the repository and the submission still reads Fake Store only.

9. **A second opinion, pasted in.** I asked another AI assistant for a UI
   audit and pasted its report into the session. The AI did not apply it
   wholesale. It checked each point against the current code and found the
   audit described the old design: six points were already done, three were
   still valid and were built with tests (category links when a search finds
   nothing, a "Continue browsing" button after the thank-you, a loading
   pulse), and four were declined with a reason each (for example a welcome
   banner, which would break the fit-one-screen rule).

10. **"Can the API detect categories and add them automatically? Even nested
    ones?"** The AI checked the code before answering: categories were
    already derived from the products, which is why 24 appeared with no code
    change. For nesting it recommended against building it, because Fake
    Store sends one flat category per product and I would be inventing data.
    It is written up as a growth path in `DECISIONS.md` instead. Same pattern
    for "do we need search on the enquiry page?": it argued for leaving it.

11. **"Once again review it all."** Two fresh reviewers, neither shown the
    AI's own opinion of the work: one read the whole repository as a hiring
    panel would, one reviewed only the web client's layout and
    accessibility. Between them they found real faults the earlier rounds
    and the AI itself had missed (listed below as items 10 and 11). Every
    finding was checked against the code before it was fixed or declined,
    and each fix came with a test or a measurement at ten window sizes.

12. **"Debounce and other techniques?"** The AI did not add debounce. Search
    here is a form that is submitted, so there is no stream of keystrokes to
    hold back; debounce only matters for search-as-you-type, which the brief
    does not ask for. It listed what is already in place instead (one cache
    with shared in-flight requests, time limits on every outside call, rate
    limiting, streaming with placeholders, lazy images).

13. **A failure and hostile-input pass.** The AI tried to break the running
    app instead of confirming it worked: 51 HTTP checks plus browser checks
    (including console errors, blocked resources and phone widths). What it
    found and left as is is listed
    in `DECISIONS.md`: unknown pages answer 200 with a not-found page, a
    malformed percent-encoded address gets Next.js's plain 500, and with the
    database down the home page is slow and enquiries ask to try again. The
    same pass added security headers to the web pages.

## Where the AI got something wrong, and how it was caught

1. **Rate limiting: wrong twice.** The first version limited enquiries per IP
   address, but the browser never calls the API; the Next.js server does, so
   every customer would have shared one limit. The AI caught that itself and
   forwarded the customer's address from the web server. The review then
   showed that fix was only half right: it forwarded the *left-most*
   `X-Forwarded-For` entry, which the browser controls, and the API port was
   published on all interfaces, so the limit could be dodged by sending a
   fake header. Three of the four reviewers found this independently, and the
   original tests had locked the wrong behaviour in. Fixed: the right-most
   entry is forwarded, the API is bound to 127.0.0.1, the tests now assert the
   forged entry is ignored, and `DECISIONS.md` says plainly that the limit is
   best-effort without a load balancer in front.

2. **Outdated Next.js knowledge.** Two things in Next.js 16 differ from what
   the model would have written from memory: error pages receive `retry` (not
   `reset`), and with the default "cache components" setting every data read
   must be cached or wrapped in `<Suspense>`. Caught because `web/AGENTS.md`
   told it to read the bundled docs first, and it did.

3. **A second enquiry was impossible.** After sending an enquiry, going back
   to the product and pressing Enquire again showed the old "Thank you" and no
   form. Next.js 16 keeps visited pages alive and hidden instead of removing
   them, so the form kept its state. The builder's own browser run never tried
   a second enquiry; the client reviewer did, and found the documented fix in
   the bundled Next.js guide. Fixed, with a unit test that reproduces the
   hide-and-return, confirmed to fail without the fix, plus a browser test.

4. **Search that looked broken.** Plain substring matching made "men" return
   all the women's clothing ("wo**men**'s"). Found by the panel and backend
   reviewers. Fixed: words must match from their start; tests added.

5. **Claims that were stronger than the code.** The first `DECISIONS.md`
   said a re-skin was "an edit to one file" while two colours and every font
   size were hard-coded; it said the client knew nothing about Fake Store
   while the client hard-coded US dollars "because Fake Store has no currency
   field"; and it called the snapshot source "proof" of the seam while it
   reused the Fake Store mapper. Found by the panel reviewer. Fixed in code
   (tokens, currency on the product, snapshot stored in the catalogue's own
   shape) and the remaining claims were reworded to match.

6. **Docker setup that would trip a reviewer.** Found by the run-it reviewer,
   by reading the files since Docker could not run:
   - MongoDB was published on port 27017, so anyone already running MongoDB
     locally would see the stack fail after several minutes of building.
   - The README told developers to set `SMTP_HOST=localhost` in `.env`, which
     the Docker run also read, breaking email inside Docker.
   - If Fake Store was down on first start, every page failed.
   Fixed: MongoDB and SMTP are no longer published (a separate dev compose
   file does that), SMTP is fixed to the Mailpit container, and the API falls
   back to the bundled snapshot when Fake Store is unreachable.

7. **Smaller things the AI caught itself:** validation messages that showed
   library jargon to customers; a dependency conflict it could have forced
   with `--force` but traced to mismatched Node type definitions instead; and
   a crash on Windows in the featured-products command caused by calling
   `process.exit` while a network handle was closing.

8. **The redesign, wrong in ways only real data showed.** All caught by
   measuring pages or by the larger sample, not by reading the code:
   - To stop one search result becoming a giant tile it capped tile width,
     which also shrank the home page's large first tile to half its space.
   - Photo padding was a percentage of tile width, so wide, short tiles
     showed thumbnail-sized photos.
   - A long price ("$1,899.99") wrapped the rating onto a second line and
     made that one tile shorter than its neighbours. Fake Store has no price
     long enough to trigger it.
   - The page frame's minimum height was one pixel taller than a 1280x593
     window, so that size scrolled by a pixel.
   - The first "fits the screen" version only worked for exactly five
     products. I asked what happens with more data; the answer became
     rule 8 in `AGENTS.md`.

9. **Its own review was too soft.** Asked "UI looks good?", the AI graded
   its own design as fine. An independent reviewer would not have had that
   bias; I should have asked one earlier.

10. **Found by the final panel review.**
    - The cache and the bundled snapshot were wired in the wrong order: one
      failed call to Fake Store could swap live data for the snapshot for
      five minutes. The order was reversed and three tests now exercise the
      wiring exactly as the app builds it.
    - A mail server that accepted the connection and then went silent would
      have kept the customer waiting. Sending now has a 6-second limit.
    - An empty product list from the source was treated as "the shop is
      empty" instead of "the source is broken".
    - Several sentences in the documents promised more than the code did
      (offline use while photos still load from Fake Store; "any SMTP
      provider"). They were reworded to what is true.
    - One suspicion was checked and cleared, not assumed: that the
      TypeScript 7 compiler would not run in the Alpine images. Its Linux
      binaries are statically linked.

11. **Found by the final web review.**
    - Product lists that scrolled inside the page could not be scrolled
      from the keyboard. They are now a named, focusable region.
    - The fit-one-screen frame switched on at 901 pixels wide, where it was
      cramped. It now needs 1100 by 560 pixels; below that pages scroll.
    - The large first tile on the home page assumed exactly five products.
      It now applies only when there are five.
    - Product cards carried a label that hid their category and rating from
      screen readers.
    - The fix for that introduced a new fault that reading the code did not
      show: hidden text inside a scrolling list stretched the page by
      thousands of pixels. The measuring script caught it on the next run.

12. **A layout patched per item count.** Adding the grid view, the AI first
    left an empty fourth column when a group had three products, then
    "fixed" it by stretching three tiles to fill the row, so tiles changed
    size from page to page. That broke rule 8 in `AGENTS.md`, which the AI
    had written itself. I asked for one rule applied everywhere; the result
    is a single grid with a "Top rated" badge, and a browser test that every
    tile on the page is the same size.

13. **Joining two head scripts broke the pre-paint script.** Adding the
    light/dark switch, the AI merged the view and theme scripts into one.
    One of the strings it used was exported from a `"use client"` file, so
    on the server it arrived as a client reference, not as text, and the
    script that sets the look before the first paint broke. Caught by the
    console-error check in the browser run. Fixed by moving the script and
    its keys to `web/src/lib/headScript.ts`, which has no `"use client"`.
