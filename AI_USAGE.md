# AI usage notes

## Tools and models

- **Claude Code** (VS Code extension), one session. Models: Claude Fable 5.2
  for planning, the first build and the later redesign; Claude Opus 5.5 for
  the first review round. It read the brief, proposed the design, wrote the
  code, tests and first drafts of these documents, and ran the checks.
- **Review subagents**: four independent Claude Code reviewers, started in
  parallel from the same session, each given only the brief and the code (not
  the builder's conclusions). See moment 3.
- **A separate Claude session** produced one screen-by-screen UI audit, which
  I pasted into the main session (moment 5). Claude was the only AI tool used
  on this project.

**About the commit history.** The work was done in one long session and
committed as logical steps (API, web, end-to-end tests, containers, docs)
once the first version worked. The history shows the shape of the result,
not the order in which it was typed. Each later round of changes was
committed the same way, as one or two commits at the end of the round.

## Agent instruction files (committed)

- [`AGENTS.md`](AGENTS.md): the project's rules for any AI agent. Eight
  boundaries that protect the seams, how to work, and the checks to run.
  Rule 8 (no page may assume how much data arrives) was added after the
  redesign, from layout bugs the larger data sample exposed (moment 4).
- [`CLAUDE.md`](CLAUDE.md): points Claude Code at `AGENTS.md`.
- [`web/AGENTS.md`](web/AGENTS.md): generated by Next.js. It tells agents that
  this Next.js version differs from their training data and to read the docs
  bundled in `node_modules/next/dist/docs/` first. This file mattered twice:
  see "where the AI got something wrong", items 2 and 3.

## Plan

There was no separate spec file. The plan was agreed in the chat before any
code, in this order:

1. The AI read the brief and listed the acceptance criteria, the hard rules
   and the gaps left on purpose.
2. Stack chosen, then the two risky parts of that choice settled (below).
3. Each technical constraint mapped to a concrete approach, one row each
   (stack, data only through the backend, AWS-compatible containers, one
   command to run, no secrets, no paid services).
4. Build order: backend rules and tests first, then the HTTP layer, then the
   client, then containers, then a full run in a real browser, then documents.
5. Independent review by four reviewers, fixes, and a full re-verification.
6. A redesign of the client, page by page, then a second independent review.

## Key prompts and moments

1. **Brief and constraints before code.** My first prompts were "understand
   the prompt and tell me" and "check the technical constraints and tell me
   the proper way", before any code. That produced the list of gaps the brief
   leaves open (who chooses the five products, where email goes with no paid
   provider), which became the assumptions table in `DECISIONS.md`, and a
   one-row-per-constraint plan. It also surfaced the one real risk in my
   stack: a reviewer asking "which one is your backend?". Rule adopted:
   Next.js renders pages only; Express owns all data and rules.

2. **My stack, challenged, then decided.** I asked for "MERN Next TypeScript".
   The AI pointed out that MongoDB is not needed for the catalogue itself,
   because Fake Store already returns products, categories and ratings, and
   offered three options: cut it, copy every product in, or give it a small
   role. It went ahead with the small role (the five chosen products and the
   enquiries) without waiting for my pick. I reviewed that and kept it.
   Products stay with the product source, so changing the source never means
   a data migration; copying them in would make us the owner of data someone
   else keeps up to date; cutting MongoDB would lose an enquiry whenever the
   email failed. It is free, runs in the same `docker compose up`, and has
   AWS-hosted equivalents (DocumentDB, or MongoDB Atlas on AWS).

3. **Independent reviewers, not self-review.** The AI graded its own first
   design "good enough", so I stopped asking it to judge its own work. Instead
   I had it start reviewers that were given only the brief and the code,
   never the builder's conclusions: first four in parallel (a hiring reviewer
   trying to run it in 10 minutes, a principal engineer scoring the five
   areas, a backend and security reviewer, a browser-based client reviewer),
   later two more for a final pass. Each had to mark findings "verified" or
   "suspected" with file and line. A finding raised by two or three reviewers
   independently was treated as real. Every high and medium finding was fixed
   with a test, or written down in `DECISIONS.md` where fixing was the wrong
   call. Most of the bugs listed below were found this way.

4. **My requirements turned into measurements.** I added two rules the brief
   does not state: every page fits one laptop screen at 100% zoom, and the
   layout must keep working "even if we add more data to the API". The AI
   turned both into scripts: one opens every page at ten window sizes in
   both looks and compares page size with window size; for "more data" it
   pointed the backend at a 194-product, 24-category sample in Fake Store's
   shape, by changing one setting and no code. Those runs found layout bugs
   that reading the code never would, and rule 8 in `AGENTS.md` came out of
   them. Near the end I asked it to try to break the app instead of
   confirming it worked: 51 hostile HTTP checks, the backend, product source,
   mail server and database each taken down, and browser checks for console
   errors. That pass added security headers and is where the limits listed
   in `DECISIONS.md` come from.

5. **Taste and scope calls stayed mine.** I rejected the AI's first design
   outright ("I don't like the design"); it offered three directions and I
   chose two, built as the light and dark looks of one design, page by page.
   When I pasted in a UI audit from a separate Claude session, the AI checked
   each point against the current code instead of applying it: six were
   already done, three were built with tests, four were declined with a
   reason. And it pushed back on features I floated when they were not worth
   it: no debounce (search is a submitted form, not search-as-you-type), and
   no nested categories (Fake Store sends one flat category, so nesting would
   mean inventing data). Both are written up as growth paths instead.

## Where the AI got something wrong, and how it was caught

1. **Rate limiting: wrong twice.** The first version limited enquiries per IP
   address, but the browser never calls the API; the Next.js server does, so
   every customer would have shared one limit. The AI caught that itself and
   forwarded the customer's address. The review then showed the fix was only
   half right: it forwarded the *left-most* `X-Forwarded-For` entry, which
   the browser controls, so the limit could be dodged with a fake header.
   Three of the four reviewers found it independently, and the original tests
   had locked the wrong behaviour in. Fixed: the right-most entry is used, the
   API is bound to 127.0.0.1, the tests assert the forged entry is ignored,
   and `DECISIONS.md` says the limit is best-effort without a load balancer.

2. **Outdated Next.js knowledge.** Two things in Next.js 16 differ from what
   the model would have written from memory: error pages receive `retry` (not
   `reset`), and with "cache components" every data read must be cached or
   wrapped in `<Suspense>`. Caught because `web/AGENTS.md` tells agents to
   read the bundled docs first.

3. **A second enquiry was impossible.** After one enquiry, going back to the
   product and pressing Enquire again showed the old "Thank you" and no form:
   Next.js 16 keeps visited pages alive and hidden, so the form kept its
   state. The builder's own browser run never tried a second enquiry; the
   client reviewer did. Fixed with a unit test that fails without the fix,
   plus a browser test.

4. **Claims stronger than the code.** The first `DECISIONS.md` said a re-skin
   was "an edit to one file" while colours and font sizes were hard-coded,
   and that the client knew nothing about Fake Store while it hard-coded US
   dollars. Found by the panel reviewer. Fixed in code (design tokens,
   currency carried on the product), and the remaining claims reworded.

5. **A layout patched per item count, which I rejected.** Adding the grid
   view, the AI first left an empty column when a group had three products,
   then "fixed" it by stretching those tiles, so tile size changed from page
   to page. That broke rule 8, which the AI had written itself. I asked for
   one rule applied everywhere: the result is a single grid with a "Top
   rated" badge, and a browser test that every tile is the same size.

6. **Tiles that jiggled while scrolling, which I caught.** I saw tiles move
   while scrolling and sent a screen recording. The AI's first checks
   (element positions and layout-shift events) showed nothing, because the
   fault was in painting, not layout. It then recorded the browser's real
   frames and measured them: the badged tiles' photos were drawn about 30
   pixels behind their row. The cause was a style it had added earlier
   (`isolation` on the photo box). Removing it took the misaligned frames
   from 9-12 per run to 0.

7. **A merged script broke the pre-paint step.** Adding the light/dark
   switch, the AI merged two small scripts into one; one string came from a
   `"use client"` file and reached the server as a reference, not text.
   Caught by the console-error check. Fixed by moving the script to
   `web/src/lib/headScript.ts`.

**Smaller findings**, each fixed with a test or a measurement:

- Search matched inside words, so "men" returned women's clothing; words now
  match from their start (panel and backend reviewers).
- The Docker setup would have tripped a reviewer: MongoDB clashed with a
  local one on port 27017, and a dev setting in `.env` broke email inside
  Docker (run-it reviewer).
- The cache and the bundled snapshot were wired in the wrong order, so one
  failed call could serve the snapshot for five minutes (final review).
- A silent mail server would have kept the customer waiting; sending now has
  a 6-second limit (final review).
- Scrolling product lists could not be reached from the keyboard (web
  review).
- Hidden "Rated" text inside a scrolling list stretched the page by
  thousands of pixels (caught by the measuring script).
- The first "fits the screen" layout only worked for exactly five products
  (caught by the larger sample).
- Customer-facing validation messages showed library jargon, and the
  featured-products command crashed on Windows (caught by the AI itself).

## What was not verified

- `docker compose up --build` itself. Both compose files pass
  `docker compose config`, the images' Alpine native packages were checked in
  the lockfiles, and the same built code (including the web standalone
  server the image runs) passed all 12 browser tests outside Docker. But the
  images were never built or started: the machine I built this on has Docker
  Desktop installed, but it does not start ("Docker Desktop is unable to
  start"), because the Windows Subsystem for Linux is not installed and I do
  not have admin rights to install it. This is the first thing a reviewer
  runs, so it is the largest unverified risk in the submission.

## Time spent

All in one day (20 November 2026), from 11:33 to about 17:05, with one
break of about 25 minutes. The total comes from the session log; the split is
my estimate, because building, testing and fixing were interleaved.

| Activity | Time |
|---|---|
| Planning (reading the brief, choosing the stack, checking constraints) | about 15 min |
| Building (AI writing code, me directing; includes the redesign, view switch, HTML email and light/dark switch) | about 2 h 45 min |
| Testing (automated tests, browser runs, layout measurements, failure tests) | about 1 h 15 min |
| Reviewing (independent review rounds and their fixes) | about 50 min |
| **Total** | **about 5 h 5 min** |

That is about twice the 2–3 hour time-box. Most of the extra went into the
four additions listed in `DECISIONS.md` ("What the brief needed, and what I
added"), which I would cut in a three-hour redo.
